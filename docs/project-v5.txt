# RE:MEMORY — Adaptive Memory Router
## OPEN LAB 2026 競賽開發總指令 V5.0

### 1. 專案使命

你現在是 RE:MEMORY 的首席開發工程師。

請建立一個真正可執行、可操作、可測試、可量化驗證的 AI 記憶路由系統，參加 OPEN LAB 2026 AI Build Challenge，主攻主辦獎、最佳創意獎及 MixRoute 特別獎。

投稿截止：2026/11/27 23:59（台灣時間）。

已取得 MixRoute US$50 API 開發額度，實際餘額及有效期限須確認。

本專案不是設計文件任務。必須實際開發程式、執行測試及產出參賽作品。

### 2. 核心問題

現有 AI 系統存在以下問題：

- 完整讀取歷史造成 Token 消耗過大。
- 對話壓縮可能遺失重要資訊。
- 語意搜尋可能忽略間接相關的資訊。
- 使用者不一定使用正式專案名稱。
- 更換模型或 Agent 時容易失去工作脈絡。
- AI 無法確定自己是否掌握足夠的資訊。
- AI 可能重複執行已完成的工作。

本系統必須研究如何在有限 Token 預算下，透過循序探索、個人化語意理解及記憶完整性檢查，正確重建工作情境。

核心標語：

**AI 可以忘記，但人類的努力不能歸零。**

### 3. 開發方法

採用 Kiro Spec-Driven Development 思想，建立可由 Codex、Kiro 或其他 Agent 共同接手的規格管理方式。

每個核心模組必須具備：

- requirements.md：需求及驗收標準。
- design.md：架構、演算法與資料結構。
- tasks.md：任務、依賴及實際進度。
- tests：可執行驗收測試。

建立全域 AGENTS.md，以及專案 Steering 規則。

但不得花費過多時間撰寫文件而延誤實作。

### 4. 核心架構

Human Intent
→ Intent Parser
→ Entity Resolution
→ Adaptive Memory Router
→ Context Reconstruction
→ Memory Coverage Engine
→ MixRoute Model Router
→ Task Orchestrator
→ Result Validator
→ Memory Writeback

各模組必須可獨立測試及替換。

### 5. 核心展示案例

使用者輸入：

「我要你繼續做昨天的音樂專案。」

系統不得直接將全部歷史交給 LLM。

應執行以下流程：

1. 解析使用者意圖：
   - 時間：昨天。
   - 主題：音樂。
   - 物件：專案。
   - 行為：繼續執行。

2. 搜尋昨日活動紀錄。

3. 找出候選專案，例如：
   - 轉換音檔。
   - 鋼琴樂理教材。
   - 人生冒險島。
   - AI 工作管理。

4. 綜合比較候選專案。

5. 若吻合度不足，探索更多線索：
   - 使用者歷史稱呼。
   - 專案別名。
   - 相關主題。
   - 檔案名稱。
   - 歷史工作行為。
   - 尚未完成的工作。
   - 專案關聯。

6. 根據新線索產生下一輪搜尋條件。

7. 重複搜尋、評分、排序。

8. 達到目標辨識條件後鎖定專案。

9. 讀取接續工作所需的最少必要記憶。

10. 檢查重要限制、證據、依賴及版本。

11. 使用 MixRoute 選擇模型。

12. 執行下一步工作並驗證成果。

13. 將新成果及經確認的新稱呼寫回記憶。

若有多個可能專案，或證據不足，不得擅自選擇後執行高風險操作。

展示案例一律使用合成資料，不得讀取使用者其他真實專案作為公開參賽資料。

### 7. 個人化語意字典

建立 User Semantic Dictionary。

同一專案可以存在多個稱呼，例如：

PROJECT-028：音訊轉換系統

可能稱呼：

- 音樂專案。
- 轉換音檔。
- 轉譜工具。
- MIDI 專案。
- 樂器分離。
- 音樂轉 PDF。

每筆稱呼關係保存：

- 專案 ID。
- 使用者 ID。
- Alias。
- 來源證據。
- 使用次數。
- 最近使用時間。
- 建立方式。
- 確認狀態。
- 關聯強度。
- 是否有歧義。

別名狀態：

CANDIDATE、CONFIRMED、REJECTED、DEPRECATED。

使用者確認過的稱呼與 AI 自動推論的稱呼必須區分。

允許一個別名指向多個專案，不可強制一對一。

### 8. 六層漸進式檢索

L0：專案 ID、名稱、日期、活動紀錄。

L1：標籤、別名、人物及關係索引。

L2：全文搜尋、語意向量、候選排序。

L3：專案摘要、重要事實、目標、工作狀態。

L4：相關歷史對話片段、決策及限制。

L5：完整原始文件、程式、事件及證據。

原則：

- 從低成本層級開始。
- 取得足夠資訊即停止深入。
- 不因為分數高就跳過必要限制檢查。
- 不重複讀取相同版本的資訊。
- 每次升級檢索層級必須記錄原因。
- 每次檢索必須記錄新增資訊及成本。
- 盡量使用本機 SQL、全文搜尋及圖譜演算法。
- 不需要大型語言模型的工作，不得浪費 API 額度。

### 9. 多維度專案辨識引擎

初始評分構面：

| 構面 | 初始權重 |
|---|---:|
| 時間吻合度 | 20% |
| 主題吻合度 | 20% |
| 使用者命名習慣 | 20% |
| 歷史行為關聯 | 10% |
| 專案內容吻合度 | 15% |
| 未完成工作關聯 | 10% |
| 近期使用頻率 | 5% |

以上權重只是初始假設，必須經測試調整。

評分引擎必須支援：

- 動態權重。
- 缺失資訊處理。
- 正向與反向證據。
- 候選專案差距。
- 時間範圍擴展。
- 已確認別名加權。
- 多義詞處理。
- 證據來源追蹤。
- 相關證據去重。
- 吻合度與實際信心校準分離。

不可將加權分數直接宣稱為正確機率。

### 10. 迭代探索引擎

每次搜尋結果都可能成為下一次搜尋的線索。

實作 Search State：

- 已搜尋條件。
- 候選物件。
- 目前評分。
- 已發現線索。
- 尚未驗證線索。
- 正向證據。
- 反向證據。
- 已讀取資訊。
- 剩餘 Token 預算。
- 剩餘 API 預算。
- 下一輪搜尋策略。

迭代流程：

解析 → 搜尋 → 評分 → 分析差距 → 發現線索 → 擴展搜尋 → 重新評分。

下一輪搜尋應優先選擇最有可能區分候選專案、且成本最低的線索。

停止條件：

- 證據足以鎖定目標。
- 已無新的有效線索。
- 候選差距無法進一步縮小。
- 達到搜尋輪數上限。
- 達到 Token 或 API 預算上限。
- 需要使用者確認。

必須避免搜尋無限迴圈。

### 11. 記憶完整性檢查

正確辨識專案，不等於已掌握完整工作情境。

建立 Memory Manifest：

- project_id。
- goal_version。
- active_task。
- mandatory_memory。
- required_dependencies。
- unresolved_conflicts。
- evidence_references。
- missing_information。
- memory_snapshot。
- token_budget。

根據任務類型，強制檢查：

- 最新目標。
- 使用者限制。
- 已完成工作。
- 未完成工作。
- 重要決策。
- 依賴關係。
- 原始證據。
- 成果是否真的存在。
- 資訊是否已過期。
- 尚未處理的衝突。

定義已知必要記憶覆蓋率。

不得將已知必要記憶覆蓋率 100%，宣稱為掌握全部歷史資訊。

若必要資訊不足，觸發 Semantic Page Fault，進行補充讀取或阻止執行。

### 12. 動態 Token 管理

建立 Context Budget Manager。

每次請求必須計算：

- 模型上下文上限。
- System Prompt Token。
- 使用者輸入 Token。
- 強制記憶 Token。
- 工作情境 Token。
- 證據 Token。
- 工具描述及結果 Token。
- 預留輸出 Token。
- 安全餘裕。

提供 1K、2K、4K、8K、16K 等不同上下文預算測試，無法容納必要指令時應標記不可行。

必要記憶超出預算時：

1. 移除重複資訊。
2. 使用具來源的結構化表示。
3. 拆解任務。
4. 分階段驗證。
5. 必要時停止並回報缺失。

不可任意截斷硬性限制。

記憶索引建立、更新、檢索、重試、推理及驗證的全部 Token 成本都必須納入統計。

### 13. MixRoute 整合

必須真正串接 MixRoute API。

先查閱官方最新文件，驗證：

- API Base URL。
- 模型清單與實際 Model ID。
- 一般 API Key。
- Smart Routing API Key。
- 授權模型池。
- Token Usage 回傳格式。
- 路由結果回傳格式。
- 計價與額度限制。

提供兩種執行模式：

A. Fixed Model。

B. MixRoute Smart Routing。

至少支援：

- 真實 API 呼叫。
- 模型選擇。
- 跨模型交接。
- 逾時。
- 有限重試。
- 可用性檢查。
- Token 統計。
- 成本計算。
- 請求 ID。
- 錯誤紀錄。
- 預算控制。

無法取得的資訊顯示 UNKNOWN，不得假造。

API Key 只能存放於本機 .env。

不得寫入前端、Git、影片、測試報告或公開紀錄。

常規 API 開發及測試總預算上限 US$35，保留 US$15 緊急預備額度。

不得自動儲值或產生額外付費。

#### B. Memory Explorer

這是最重要的展示畫面。

即時顯示：

- 使用者意圖解析。

- 候選專案。
- 多維度評分。
- 新發現的線索。

#### D. Context Inspector

- 已載入的資訊。
- 尚未載入的資訊。
- 必要資訊。
- 缺失資訊。
- 衝突。
- 記憶覆蓋率。
- Token 使用分布。
- Semantic Page Fault 紀錄。

#### E. Recovery Lab

- 清除原始對話上下文。
- 建立新的 Agent Session。
- 更換模型。
- 從持久化記憶重新搜尋。
- 重建工作狀態。
- 接續未完成工作。
- 實際產生成果。

必須確保新 Session 無法偷偷取得已清除的原始上下文。

#### F. Benchmark Lab

- 選擇測試組。
- 設定 Token 預算。
- 執行測試。
- 顯示專案辨識正確率。
- 顯示記憶召回率。
- 顯示任務成功率。
- 比較 Token 與成本。
- 匯出真實測試結果。

所有介面資料必須連接真實後端。

模擬資料必須標記為 DEMO 或 SIMULATION。

### 16. 測試資料集

建立可重現的合成資料產生器。

支援：

- 10 個專案。
- 100 個專案。
- 1,000 個專案。
- 大量歷史事件。
- 相似專案名稱。
- 相同主題但不同目標。
- 使用者非正式稱呼。
- 舊版與新版資訊。
- 時間錯置。
- 多義詞。
- 衝突記憶。
- 已完成與未完成工作。
- 缺少證據的主張。
- 文件中的 Prompt Injection 測試。

建立 Ground Truth 標準答案。

分開開發集與盲測集。

Ground Truth 不可被檢索引擎或執行 Agent 讀取。

### 17. 對照實驗

至少實作以下六種策略：

A. 最近歷史截取。

B. 固定摘要。

C. 單輪全文及語意檢索。

D. 迭代式檢索。

E. 迭代檢索＋個人語意字典＋關係探索＋記憶覆蓋檢查。

F. E 組＋MixRoute Smart Routing。

A 至 E 優先使用相同固定模型，避免將模型差異誤判為記憶架構效果。

F 組用於評估智慧模型路由的額外效益。

### 18. 評估指標

實際測量：

- Project Top-1 Accuracy。
- Project Top-3 Accuracy。
- Mean Reciprocal Rank。
- Critical Memory Recall。
- Memory Precision。
- Task Continuation Success。
- 關鍵限制遺漏率。
- 錯誤專案執行率。
- 不必要澄清率。
- 已完成工作重複率。
- 平均搜尋輪數。
- 平均檢索 Token。
- 完整端到端 Token。
- API 成本。
- 執行延遲。
- 每次成功交付成本。

研究目標：

在相同 Token 預算下，提高正確辨識與工作接續成功率；或者在相近品質下減少 Token 消耗。

不得預先假設新架構一定勝出。

實際結果不理想時，記錄原因並改進。

### 20. 安全及治理

- 所有 SQL 使用參數化查詢。
- 文件及記憶內容視為不可信資料。
- 防止 Prompt Injection 改變系統權限。
- API Key 只由後端管理。
- 不允許任意 Shell 指令執行。
- 專案資料隔離。
- 使用白名單工具。
- 所有高風險操作需要明確授權。
- 限制檔案讀取範圍。
- 限制 Token、成本及最大執行輪數。
- 使用交易機制及成果識別碼，避免重複執行。
- 不得掃描使用者整台電腦。
- 不得修改其他既有專案。
- 不得自行公開部署或投稿。

P1：大規模測試、圖譜視覺化、自動事件監控及更多資料來源。

P0 未完成前不得任意投入 P1 或 P2。

### 23. PDCA 工作管理

每一輪工作必須執行：

Plan：選擇尚未通過的最高優先驗收項目。

Do：實際撰寫程式或修正問題。

Check：執行測試，檢查成果及證據。

Act：更新任務狀態，決定下一步。

每輪保存：

- 工作目標。
- 實際異動檔案。
- 執行指令。
- 測試結果。
- 新增成果。
- 未通過項目。
- API 成本。
- 下一步行動。

進度由通過驗收的項目計算，不接受 AI 自行推測完成百分比。

局部阻塞不等於整體專案完成。

若 API Key 尚未提供，先完成不需要 API 的功能與測試，不得停止全部開發。

- 顯示每輪吻合度變化。
- 找到正確專案，或在證據不足時提出精準確認。
